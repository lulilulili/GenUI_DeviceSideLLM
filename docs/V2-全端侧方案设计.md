# GenUI v2 全端侧方案设计（重构说明）

> 本文是 `genui_v2/` 重构的权威说明，覆盖：① 全端侧可行性与成本核算、② 布局策略（模板命中
> 与自由排版美学）、③ 模板保真度修复、④ 重构后的完整流程、⑤ 系统提示词优势与语素字段设计。
> 所有带"实测"标注的数字来自本机 Ollama qwen2.5:3b 的真实运行记录（2026-09-08）。

---

## 0. 重构总览（要求④）

```text
用户话语
→ 规则路由（能力注册表别名派生的关键词；不命中才用 12-token 模型路由）
→ 1 次 LLM 调用：MorphemeDraft v2 {"t","m":[{"l","q","f","r"}]}（≤1 次带错误重试）
→ 组件推导（derive.py，纯代码：role+f → TEXT/METRIC/STATUS/PROGRESS/SWITCH/SLIDER/BUTTON/LIST）
→ 能力绑定（capability.py：语义键 → 声明式注册表 → 数据路径/动作/权限/首帧值；未命中降级静态文本）
→ 尺寸决策 + 信息预算降级（protocol.py）
→ 布局（layout.py：18 个 PDF 原型评分匹配；<50% 覆盖转层级式自由布局）
→ RenderSpec → HTML（PDF 保真渲染）/ A2UI / DSL
```

与 v1 的关键差异：

| 维度 | v1（genui_intent） | v2（genui_v2） | 动机 |
|---|---|---|---|
| 协议 | 双协议并存（RawIntentSpec + Morpheme 含组件 k） | 单协议，模型只出 4 字段语义 | 消除"模型选组件"错误类；一个决策一个 owner |
| 组件选择 | 模型选 k，reconcile_types 关键词纠正 | 代码唯一推导 | v1 两套 owner 且规则在 63 条上过拟合 |
| 数据 | fill_mock_data 硬造 | 声明式能力注册表绑定（路径/动作/权限/首帧值） | 可信边界、可落地 |
| 领域词表 | router.py 手写关键词 | 由注册表 aliases 派生 | 单一事实来源 |
| 渲染 | 无边框自适应 grid | 令牌化 PDF 保真渲染 | 要求③ |
| 规则后处理 | 130+ 行 `_canonical_task` 词法改写 | 无（校验+重试+确定性兜底） | 成绩可信、可泛化 |

旧代码全部保留（`genui_intent/`），便于对比回归。启动新工作台：`python -m genui_v2.workbench` → http://127.0.0.1:8766 。

## 1. 全端侧可行性分析（要求①）

### 1.1 新增内存开销核算

以 qwen2.5:3b（3.09B 参数，36 层，GQA：16 Q 头 / 2 KV 头，head_dim 128）为基准：

| 项目 | 计算 | 占用 |
|---|---|---|
| 权重 Q4_K_M | 3.09B × ~0.58 B/参数 | ~1.9 GB |
| 权重 Q4_0（更省） | | ~1.7 GB |
| KV 缓存/每 token | 2(K+V) × 36层 × 2 KV头 × 128 × 2B(fp16) | **36 KB/token** |
| KV @ 2k 上下文 | 36KB × 2048 | ~72 MB |
| KV @ 4k 上下文 | | ~144 MB |
| 推理运行时（llama.cpp 计算图/缓冲） | | 200~300 MB |
| **模型侧合计（2k ctx）** | | **≈ 2.1~2.4 GB 峰值** |
| v2 管线本体（注册表索引+模板+逻辑） | 纯代码与 JSON | **< 5 MB（可忽略）** |

结论与建议：
- v2 单次调用 ≤600 token 上下文（实测 373~397 入 + 93~133 出），**2k ctx 绰绰有余**——不要按默认 32k 分配 KV，`num_ctx=1024` 即可再省 ~54MB 且加速 attention。
- 领域路由优先走规则（注册表别名派生），**不需要第二个模型**；兜底模型路由复用同一权重、只解码 12 token。
- 12GB RAM 手机可直接常驻；8GB 档建议按需加载/退出，或换 qwen2.5-1.5b（权重 ~1.1GB，总占用 ~1.4GB，本协议的封闭选择任务上损失有限）。
- NPU 路线（W4A8/W8A16）占用与 Q4 相当，收益在速度不在内存。

### 1.2 Token 减少的成本核算（实测）

| 方案 | 输入 token | 输出 token | 备注 |
|---|---:|---:|---|
| v0：完整 RawIntentSpec 协议文档 | 11,000~16,000 | ~600 | 不可用，单条 78s |
| v1 compact（intent） | ~700~900 | ~200~240 | 63 条开发集 P50 11.7s |
| v1 morpheme（含 s/z/d/k） | ~550~700 | ~120~180 | |
| **v2（本方案）** | **373~397（实测）** | **93~133（实测）** | 天气场景真机 |

v2 的省法（对应字段见 §5）：删掉 s/z/d/k 四个可推导字段；候选键注入上限 24 个；固定前缀 +
动态尾部结构使 **KV 缓存前缀复用生效——实测 prefill 由冷 971ms 降到热 429ms**。

延迟核算（输出按 120 token 计）：

| 硬件 | prefill(~400tok) | decode | 单次合计 | 含 30% 重试率均摊 |
|---|---|---|---|---|
| 桌面 CPU（实测环境） | 0.4~1.0 s | 8~11 s（≈11 tok/s） | 9~12 s | 12~16 s |
| 旗舰手机 CPU（8 gen3 级） | ~0.5 s | 6~10 s（12~20 tok/s） | 7~10 s | 9~13 s |
| 旗舰 NPU（W4A8） | <0.3 s | 2.4~6 s（20~50 tok/s） | 3~6 s | 4~8 s |
| qwen2.5-1.5b @ NPU | <0.2 s | 1.5~3 s | **2~3.5 s** | 2.5~4.5 s |

> 重要：**输出 token 是延迟主项**。v2 把输出压到 ~100 token 是比压输入更大的提速来源；
> 进一步手段是让二次重试只输出 `m` 数组 diff（未实现，收益 ~30%）。

### 1.3 全端侧流程准确性预期

按阶段拆（结构性指标可保证，语义性指标是预期区间，**须以未参与调参的冻结测试集验收**——
这是 v1 评测文档已自我指出、v2 继续坚持的红线）：

| 阶段 | 机制 | 预期 |
|---|---|---|
| JSON/枚举结构合法 | Ollama `format=json_schema` 约束解码 + 校验器 | **≈100%（保证）** |
| 领域路由 | 注册表别名规则 → 12-token 模型兜底 | 92~97% |
| 语素语义正确（字段选取+角色） | 短提示+1例few-shot+候选键注入+1次纠错 | 80~90%（3B）；1.5B 再降 5~8pt |
| 能力绑定 | EXACT→ALIAS→TOKENS 三级解析 | 注册表内 ≥95%；表外 100% 安全降级为静态文本 |
| 布局 | 确定性评分匹配 + 自由兜底 | 不失败（100% 出卡） |
| **端到端"渲染出合理卡片"** | 上述全链 + 预算降级 | **≈99%（出卡）；语义完全正确 75~88%** |

真机一例佐证机制有效性：天气场景第 1 次输出违反"恰好 1 个 PRIMARY"被校验器拒绝，
带错误重试后第 2 次把 PRIMARY 正确落在"是否会下雨"（用户问题重心）上，4 语素全部 EXACT 绑定。

### 1.4 系统 API 的注册与获取形式（推荐）

三种形态对比：

| 形态 | 说明 | 评价 |
|---|---|---|
| (a) 静态打包 JSON | 能力清单随应用打包（本 demo `capability.py`） | 适合演示/一方能力固定集 |
| (b) 运行时能力服务 | 系统 IDL/IPC 实时查询可用能力 | 实时准确但引入进程依赖与延迟 |
| (c) **声明式清单 + 安装期聚合（推荐）** | 每个应用/系统服务随包声明能力清单（HarmonyOS InsightIntent / CreateMyCard provider.json 同款思路），框架在安装/升级时聚合进端侧索引，运行时只查本地索引 + 权限门禁 | 兼得离线、低延迟、可审计、按 App/ROM 版本区间灰度 |

清单条目字段（v2 已按此实现）：

```json
{"key": "phone.battery.level",          // 稳定语义键（提供方版本化）
 "aliases": ["电量","电池","battery"],   // 路由与模糊解析词；同时派生领域词表
 "path": "/device/battery/level",       // 运行时写入的数据模型 JSON Pointer
 "valueType": "PERCENTAGE",             // 声明形态：绑定后覆盖模型的猜测
 "sample": 67, "unit": "%",             // 首帧/预览值（生产用最近缓存值）
 "action": {"call":"toggleAbility"},    // 白名单动作描述符（deeplink/intent id）
 "permission": "ohos.permission.X",     // 绑定前由宿主校验，不进提示词
 "freshness": "PUSH"}                   // PULL 展示时拉取 / PUSH 订阅推送
```

安全不变量：**模型永远不接触真实 API 名、deeplink、权限串**——提示词里最多注入语义键候选；
绑定由解析器在本地索引内完成，表外键一律降级静态文本，绝不执行。

## 2. 布局设计（要求②）

### 2.1 已有设计模板：如何尽可能命中、命中后尽可能接近

**提示词/结构需要调整吗？需要，而且 v2 已经调整——核心思路是"让草稿天生长成模板的形状"，
而不是事后修补：**

1. **角色词表 = 模板槽位词表。** `r` 的枚举（PRIMARY/SECONDARY/SUPPORTING/*_ACTION/WARNING）
   就是 18 个 PDF 原型槽位声明的角色，模型输出的天然是槽位匹配的输入。
2. **提示词硬约束成原型形状**：恰好 1 个 PRIMARY、最多 2 个 ACTION、按尺寸限条数——每一条
   都对应原型的容量结构，且由校验器强制（真机已验证会拒绝+重试）。
3. **组件先推导后匹配**：组件由代码从 (r,f) 推导，槽位 FAMILY 兼容按构造成立，杜绝
   "模型选了 SWITCH 而槽位只收 BUTTON"这类假性未命中。
4. **预算先降级后匹配**：超容量草稿先按优先级降级到原型容量内，而不是带着超载去匹配失败。
5. **评分与放置**（沿用并保留 v1 优点）：EXACT>FAMILY>FOOTPRINT 三级兼容 + 角色加分 +
   显著度加分；近优带内用语义签名稳定选型（同分不撞脸）；未匹配语素放入模板留白
   （TEMPLATE_EXTENDED）；覆盖率 <75% 且有放不下的才弃模板。
6. **命中后尽可能接近 PDF**：匹配只决定"谁进哪个槽"，视觉全部走设计令牌（§3），
   所以命中原型的卡与 PDF 的差异只剩内容本身。

### 2.2 不得已进入自由排版：什么样更美观

v1 的自由兜底是均匀网格（每项 3 行等分）——这正是 PDF 卡片"不会"做的事。v2 换成
**层级式构图**，规则全部来自参考页的视觉语法：

1. **主视觉带**：恰好一个 PRIMARY/WARNING 占顶部 ≥40% 高度、全宽——每张 PDF 卡都有唯一焦点；
2. **细节网格**：SECONDARY/SUPPORTING 按 2 列（2x2）/3 列（3x2/3x3）对齐排布，共享列线与
   8px 沟槽；LIST 独占整行；
3. **底部操作条**：≤2 个动作固定在底部（12 行制高 3 行），1 个全宽胶囊、2 个对半分——
   与 PDF 的按钮位置一致；
4. **克制的视觉预算**：两档文字色（内容/辅助）+ 一个强调色；两种字号 + 一个大数字；
   统一圆角与内边距——不做逐槽底色、不平均切碎画布；
5. **2x1 特例**：左信息右图标位的胶囊构图（主+辅上下两行，动作固定右侧圆位）。

## 3. 模板保真度修复（要求③）

差异根源：v1 渲染器输出无边框、自适应高度的裸 grid + 默认字体，没有卡片"chrome"。
v2 从 PDF 参考页实测提取设计令牌（`genui_v2/tokens.py`），渲染器（`render.py`）按令牌绘制：

| 度量 | PDF 实测 | v2 令牌 |
|---|---|---|
| 2x1 画布 | 宽高比 ≈2.6~3.2 的胶囊条 | 320×100，圆角 32（≈h/3） |
| 2x2 画布 | 正方形，圆角/边长 ≈0.2 | 190×190，圆角 38 |
| 3x2 / 3x3 | 宽条 / 大方 | 400×190 / 400×400，圆角 38/40 |
| 图标位 | 右上/右侧圆形色块 | 32~40px 圆 chip，语义 glyph（图片资源不强求） |
| 焦点数值 | 32~38px 粗体 + 小单位 | hero 34/700 + unit 14/600 |
| 标题/辅助 | 12~13px 次级色 | label 12/500，辅助色两档 |
| 按钮 | 半透明胶囊，白字 | pill 高 34、全圆角、透明白底 |
| 进度 | 环形 | conic-gradient 环 + 中心值 |
| 用色 | 白底深字 或 渐变底白字 | 5 套预设（light/blue/violet/teal/orange），按领域自动 |
| 投影 | 卡片悬浮感 | 统一 soft shadow |

原则：**模板只声明结构（槽位），不复制视觉常量；所有视觉走令牌层**——换主题/深色模式只动
tokens.py，18 个原型与自由布局同时受益。

### 3.1 标签消隐（label elision）——何时组件自己的文字可以隐藏

PDF 参考卡从不给"26°+☀"写"温度"，但"空气质量:优"必须带标签。这个区分是可计算的
（`genui_v2/elision.py`，管线独立阶段，裁决与理由在工作台语素表可见）：

**当且仅当以下全部成立才隐藏标签：**
1. **同类唯一**——卡上没有同类组件（两个进度环必须都带标签，硬规则最先判）；
2. **值自明**——单位/格式自带语义：强单位（°/°C）、DURATION/DATETIME 格式、进度环自带 %；
3. **上下文覆盖**——卡片标题已含标签的领域词（"耳机状态"覆盖"耳机电量"）。

**组件形态例外：** BUTTON 文字即标签（从不另渲）；SWITCH/SLIDER 无标签即"神秘开关"，
仅当标题字面包含标签才隐藏；STATUS/TEXT 要求标题严格包含标签（字面子串，不做模糊
匹配——"连接状态"≠"耳机状态"，因为"已连接"单独出现未必可读）；WARNING 永远保留。

**不变量：视觉隐藏≠信息删除**——被隐藏的标签保留为无障碍标签（aria-label），读屏与
长按提示不受影响。

## 4. 系统提示词的优势（要求⑤-a）

v2 系统提示词全文 ~330 字（≈220 token），其设计优势逐条说明：

1. **只描述"是什么"，不描述"怎么排"**——UI 决策全部外移，提示词不用背负布局/组件/协议规则，
   这是能砍到 330 字的根本原因；
2. **一条 few-shot 例子顶十条规则**：对 3B 模型，示例比指令的格式遵从率高得多；例子同时
   演示了字段、角色分布（1 PRIMARY + 辅 + 1 ACTION）和语义键风格；
3. **无 CoT**：3B 在结构化任务上加推理链反而退化（跑偏+破坏格式），直接作答；
4. **形状约束前置**（恰好 1 PRIMARY / ≤2 ACTION / 按尺寸限条数）：既是质量规则也是
   模板命中优化，且每条都能被校验器机读裁决——写进提示词的规则全部"可执行"；
5. **负面约束极少而精**（不编造、不合并、不添加）：只保留会造成安全/语义事故的三条，
   其余交给约束解码与校验器；
6. **固定前缀稳定**：系统提示词与 few-shot 逐字节不变，动态内容（尺寸/领域/候选键/用户话）
   全部排在尾部 → 端侧 KV 前缀缓存直接复用（实测 prefill 971ms→429ms）；
7. **格式外包**：JSON 合法性由 `format=json_schema` 约束解码保证，提示词不写引号转义类规则。

## 5. 语素设计的优点与字段功能（要求⑤-b）

语素（morpheme）是"一条用户可感知的信息或操作"的最小语义单元。相比让模型直接产 UI，
语素层的根本优点：**它是模型能力与 UI 质量之间的绝缘层**——模型只回答"用户要看什么、
什么最重要"，所有会被 3B 做错的事（组件、布局、绑定、数据、视觉）都在绝缘层之后由
确定性代码完成，因此模型错误的爆炸半径被限制在"选错信息"这一种，且可被校验器拦截。

### 每个字段承载的功能与优化效果

| 字段 | 承载什么 | 起到的优化效果 |
|---|---|---|
| `t` 标题 | 卡片主题（用户语言，可 null） | 自由布局的标题栏与语义签名稳定选型的输入；null 时不占视觉预算 |
| `m[].l` 标签 | 该信息的用户语言称呼 | 模型唯一的自由文本，承载本地化；同时作为绑定解析的辅助证据（TOKENS 级匹配）与未绑定时的安全兜底展示 |
| `m[].q` 语义键 | 简短英文键，如 `phone.battery.level` | **与能力注册表的接缝**：EXACT→ALIAS→TOKENS 三级解析定位数据路径/动作/权限；候选键注入让 3B 大概率直接命中 EXACT（真机天气场景 4/4 EXACT）；表外键安全降级，永不执行 |
| `m[].f` 数据形态 | NUMBER/PERCENTAGE/ENUM/BOOLEAN/DURATION/LIST/… | ① 组件推导的主输入（PERCENTAGE→环形进度、BOOLEAN+ACTION→开关）；② 与注册表声明交叉校验——绑定成功后以注册表 valueType 为准，模型猜错形态零成本自愈 |
| `m[].r` 角色 | PRIMARY/SECONDARY/SUPPORTING/PRIMARY_ACTION/SECONDARY_ACTION/WARNING | 一个字段同时驱动四件事：优先级（降级顺序）、模板槽位匹配（角色词表对齐）、自由布局分带（主带/细节/操作条）、视觉强调（字号/色调）——这是"信息层级"从模型到像素的唯一传递通道 |

### 被删除的字段（删除本身就是优化）

| v1 字段 | 为何删除 |
|---|---|
| `k` 组件 | 模型最常出错的决策；(r,f) 可完全推导 → 错误类整体消失，输出省 ~15% token |
| `s` 载体 / `z` 尺寸 | 是请求输入不是模型判断；AUTO 时按语素数确定性决定 |
| `d` 密度 | 信息预算的结果而非模型的选择 |

## 6. 已验证结果（2026-09-08）
