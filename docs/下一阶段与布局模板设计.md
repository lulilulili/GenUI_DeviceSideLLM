# RawIntentSpec 之后的任务与布局模板设计

## 一、结论

布局模板可行，而且应成为 GenUI 的核心中间层，但不能把它理解成“设计师画若干固定卡片，模型选一个”。更稳妥的形态是：

```text
语义槽位模板 + 响应式布局规则 + 设计令牌 + 组件能力约束 + 语义降级策略
```

端侧模型输出业务语义，确定性代码把业务结果转换成带优先级、角色、尺寸偏好和交互能力的内容节点；布局求解器再把这些节点放入设计师定义的模板族。模型不输出坐标、CSS、组件树或模板 ID。

这样既支持首期桌面卡片，也能扩展到页面、表单、弹窗、Widget 和 Overlay。真正跨载体复用的是语义节点和编排规则，而不是某一套卡片像素布局。

## 二、模型 JSON 之后的完整任务

### 1. 建立可信边界

对模型结果执行 JSON 语法、固定字段、类型、枚举、领域动态候选、任务引用与数量上限校验。校验失败只允许一次带具体错误的纠错；仍失败则进入安全兜底，不把未知内容交给执行层。

产物：`ValidatedRawIntentSpec`。

### 2. 上下文融合与实体解析

将 `entityMention`、`referenceType`、位置和会话信息匹配到真实对象。例如“床头那个灯”可匹配设备注册表中的两个候选；“它”需要从当前页面或前一轮寻找对象。解析结果必须包含候选、置信度和来源，而不是只给一个武断 ID。

产物示意：

```json
{
  "entityRef": "device.light.bedside_1",
  "matchStatus": "UNIQUE",
  "source": "DEVICE_REGISTRY"
}
```

无唯一结果时不继续执行：如果界面可承载候选，则生成选择 UI；否则生成澄清问题。

### 3. 参数规范化

把语义表达转换为能力可理解的规范值：

- `MAXIMUM` 根据设备能力转成亮度上界；
- `RELATIVE + DECREASE + SLIGHT` 根据产品策略和当前值计算变化量；
- “半小时后”结合当前时区转成绝对触发时间，同时保留原表达；
- 单位换算、范围裁剪、默认值填充必须由代码完成。

规范化时记录来源与转换轨迹，便于解释和调试。安全敏感或不可逆操作不能仅依赖模型的 `certainty`。

### 4. 能力匹配与权限/风险判断

能力注册表根据已解析实体、操作和属性返回允许的命令、参数约束、读取能力、是否离线、权限状态以及风险级别。此时才绑定真实 Action ID。

建议状态至少包括：`READY`、`NEEDS_PERMISSION`、`NEEDS_CONFIRMATION`、`NEEDS_CLARIFICATION`、`UNSUPPORTED`、`TEMPORARILY_UNAVAILABLE`。

### 5. 数据读取或内容生成

查询类任务从可信数据源读取天气、电量和设备状态；内容类任务把意图交给内容生成器产生文案；控制类任务通常先生成“待确认命令”，只有满足授权策略后才执行。绝不能让意图模型编造这些结果。

产物：统一的 `TaskResult[]`，包含状态、数据、可用动作、错误与新鲜度。例如天气结果应携带采集时间，内容结果应携带文本与语言。

### 6. 构建语义展示模型

将领域数据映射为与具体 UI 框架无关的 `PresentationModel`。节点表达“是什么”，而不是“画在哪里”：

```json
{
  "surfaceHint": "AUTO",
  "nodes": [
    {"id":"title","role":"TITLE","content":"卧室灯","priority":100},
    {"id":"value","role":"PRIMARY_VALUE","content":"40%","priority":100},
    {"id":"control","role":"PRIMARY_ACTION","actionRef":"action.light.set","priority":90},
    {"id":"detail","role":"SUPPORTING_TEXT","content":"暖光","priority":50}
  ]
}
```

节点可以带 `minSize`、`idealSize`、`maxLines`、`shrinkPolicy`、`overflowPolicy`、`groupId`、`orderAfter`、`requiredWith` 和无障碍描述。这些由领域适配器和组件注册表确定，不由意图模型猜测。

### 7. 载体选择

编排器综合用户明确要求、入口限制、任务复杂度、交互风险、可用空间和设备形态选择 `CARD/PAGE/FORM/DIALOG/...`。用户指定不是绝对命令：例如复杂表单塞不进 2×1 时应升级为页面入口；高风险操作可能强制确认弹窗。

### 8. 模板族筛选与布局求解

先按载体、语义角色、交互模式筛选模板族，再用确定性评分选择尺寸变体。求解器负责槽位兼容、空间预算、文本测量、组合约束和降级，不让模型自由生成布局。

建议评分因素：必要节点覆盖率、首要任务显著性、交互可达性、溢出风险、设计一致性、无障碍以及历史偏好。必要节点无法容纳时必须换模板、换载体或请求澄清，不能静默删除。

### 9. 生成 RenderSpec 并渲染

`RenderSpec` 才包含模板、槽位、组件变体、设计令牌、数据绑定和动作引用。渲染器把它转换成 Compose/SwiftUI/ArkUI/HTML 等具体实现。执行层只接受能力层签发的动作引用，并再次检查权限与参数。

### 10. 观测与反馈闭环

记录阶段化指标而非只看最终截图：路由准确率、字段准确率、实体唯一匹配率、能力覆盖率、模板回退率、文本溢出率、首屏任务完成率、用户改动率、P50/P95 延迟、内存与功耗。日志需脱敏，模型版本、注册表版本、模板版本可追溯。

## 三、布局模板为何可行

业务内容虽然开放，但 UI 的视觉语法并非无限：标题、主值、状态、摘要、列表、输入、主要动作、次要动作、图像/图表等角色相对稳定。把无限的业务语义先映射到有限的展示角色，就能用有限模板覆盖大量场景。

可行性的边界也很明确：

- 模板适合约束布局语法，不适合穷举业务页面；
- 完全自由的模型坐标生成在小模型上不稳定，也难以保证品牌、无障碍和安全；
- 仅靠固定模板同样不足，会在长文本、多任务、国际化和新组件出现时失效；
- 因此需采用“模板骨架固定、槽位语义化、局部布局可求解”的混合方案。

建议逐步从领域模板族抽象共性，而不是一开始追求一个万能模板。首期卡片可以保留 `single_action`、`status_summary`、`device_control`、`progress_goal`、`list_summary`、`information` 等模板族；当验证出共同结构后，再抽取跨领域骨架。

## 四、布局模板必须满足的条件

### 1. 槽位按语义角色定义

模板声明接受 `TITLE`、`PRIMARY_VALUE`、`STATUS`、`PRIMARY_ACTION`、`LIST` 等角色，不绑定“天气温度”或“灯光按钮”。同一槽位声明允许的组件能力，而非唯一组件名。

### 2. 响应式而非固定像素

模板必须定义最小/理想/最大尺寸、断点、内边距、网格、比例、文字行数和组件伸缩策略。支持字体缩放、不同语言、横竖屏、安全区域和系统字号。

### 3. 有明确的必需项与可选项

每个模板声明必需角色、可选角色、最大重复数和共现/互斥条件。例如确认操作必须同时展示对象、后果和确认动作；只有装饰信息可以优先被移除。

### 4. 降级是语义策略

降级顺序应由领域适配器给出，例如天气 `逐小时预报 → 今日高低温 → 当前温度`，而非简单删掉最低优先级组件。每一步都必须保持核心任务可理解、可操作。

### 5. 内容容量可计算

槽位声明字符/行数预算和溢出策略：缩短、摘要、折叠、滚动、分页、跳转详情或换载体。交互控件不能通过缩小到不可触达来解决溢出。

### 6. 组件和动作受能力约束

槽位匹配依据组件注册表中的输入类型、输出角色、状态数量、交互方式、最小触控尺寸和无障碍能力。模板不能把连续值控制错误地装入二态开关，也不能让禁用动作看起来可执行。

### 7. 设计系统统一

颜色、字体、间距、圆角、阴影、动效与状态色引用 design token。模板定义结构，不复制视觉常量。亮暗模式、主题、品牌和高对比模式由 token 层切换。

### 8. 可验证且确定

相同输入、模板版本和环境应产生相同布局。模板需有静态 lint、快照/金图、极端内容、国际化、字号放大、无障碍、RTL 和交互测试。设计师工具导出的声明必须可版本化、可回滚。

### 9. 安全降级与逃生口

任何模板都要定义“不适配”条件。当节点过多、风险高、信息缺失或空间不够时，允许切换模板、提升到 Page/Dialog、拆成步骤或仅显示入口，不能硬塞。

## 五、端侧模型如何配合模板

### 应当输出

端侧意图模型继续输出当前 `RawIntentSpec`：目标、任务、对象语义、操作、参数、上下文、依赖、用户明确的载体/密度/尺寸要求与解析状态。这些信息帮助后续代码判断要展示哪些业务结果。

### 不应输出

不输出 `templateId`、`componentType`、网格坐标、宽高、颜色、字体、CSS、DSL、Action ID 和实时数据。即使将来模型能力提升，也建议把这些视作候选建议而非可信最终结果。

### 需要新增在哪里

不要为布局把大量字段塞回 `RawIntentSpec`。新增一个由代码生成的 `PresentationModel`，再由编排器生成 `RenderSpec`：

```text
RawIntentSpec（模型语义）
  + EntityResolution / CapabilityPlan / TaskResult（真实世界结果）
  → PresentationModel（语义节点、优先级、内容约束）
  + SurfaceConstraints / DesignSystem / ComponentRegistry
  → LayoutSolver
  → RenderSpec（模板、槽位、组件、绑定）
```

如果确实需要模型参与，只让模型处理代码难以判断的软语义，例如从一段内容中判断哪句话是摘要、哪些信息更值得首屏展示；输出也应是有限枚举或节点排序，并由规则复核。

## 六、建议的模板声明

```json
{
  "templateId": "status_summary",
  "version": "1.2.0",
  "surfaces": ["CARD", "WIDGET"],
  "variants": {
    "2x1": {
      "requiredRoles": ["TITLE", "PRIMARY_VALUE"],
      "slots": [
        {"id":"header","accepts":["TITLE","STATUS"],"maxItems":2},
        {"id":"main","accepts":["PRIMARY_VALUE"],"maxItems":1},
        {"id":"action","accepts":["PRIMARY_ACTION"],"maxItems":1,"optional":true}
      ],
      "capacity": {"maxTextLines":4,"maxActions":1},
      "fallback": "information_compact"
    }
  }
}
```

生产协议还应为模板加入 `layoutRules`、`accessibilityRules`、`breakpoints`、`overflowPolicy`、`allowedComponentCapabilities` 和 `telemetryTag`。模板 ID 只出现在编排阶段，不能来自用户输入或意图模型。

## 七、推荐实施里程碑

1. 冻结并评测当前 `RawIntentSpec v1.0`，先跑通五领域。
2. 定义 `EntityResolution`、`CapabilityPlan`、`TaskResult`，用真实设备/服务注册表跑通可信数据链路。
3. 定义约 10 个稳定语义角色和 `PresentationModel v0.1`，为五领域各写确定性适配器。
4. 先实现 3 个高频模板族及 2×1、2×2、3×3 变体，使用规则评分和语义降级。
5. 建立内容压力测试矩阵：空值、超长、中文/英文/德文、200% 字号、多任务、离线和权限拒绝。
6. 再扩展页面/表单载体，验证语义节点能否复用；根据数据调整角色体系与模板粒度。

最重要的验收标准不是“能生成漂亮卡片”，而是：面对未见过的业务内容，系统仍能选择安全载体、保留核心语义、无溢出地呈现并完成主要任务。
