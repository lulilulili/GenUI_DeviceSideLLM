## 一、先建立大图：我们训练的到底是什么

本项目里模型只干一件事：把用户的一句话变成 4 字段语素 JSON。

```text
输入（提示词）                          输出（我们希望模型说的话）
"手机还剩多少格电啊"          →          {"t":"手机状态","m":[{"l":"电量",
                                        "q":"phone.battery.level",
                                        "f":"PERCENTAGE","r":"PRIMARY"}]}
```

**"训练"= 给模型看几千对这样的（输入→正确输出），让它统计性地学会这个映射。**
不训练时，我们靠提示词（prompt）里的指令和例子"临场教"；训练则把这些规律
"压进"模型权重里。两者不互斥，往往组合使用。

一个必须先建立的期望管理：训练不是编程。你无法保证模型"学会规则"，只能
观察它在测试集上的行为变化。所以**评测体系比训练本身更重要**——没有考卷，
训练就是盲人骑马。这也是执行计划里"阶段 1 评测地基先于一切训练"的原因。

## 二、概念小词典（按出场顺序）

| 概念 | 一句话解释 | 在本项目里的对应物 |
|---|---|---|
| token | 模型处理文本的最小单位，约等于半个英文单词/一个汉字 | 我们的输出约 100~300 token；越短越快越稳 |
| system prompt | 每次对话固定发给模型的"岗位说明书" | `genui_v2/protocol.py` 的 `SYSTEM_PROMPT` |
| few-shot | 在提示词里放 1~N 个完整例子教格式 | `protocol.py` 的 `FEWSHOT`（1 个例子） |
| 温度 temperature | 采样随机度；0 = 每次输出尽量相同 | 评测/生产都用 0，保证可复现 |
| 约束解码 | 推理时强制输出符合 JSON Schema | `protocol.schema()`，结构合法率≈100% 的来源 |
| SFT | Supervised Fine-Tuning，监督微调：喂（输入→标准输出）对 | 我们阶段 3 要做的事 |
| messages 三元组 | SFT 样本格式：system/user/assistant 三条消息 | 实习生 `sft-144.jsonl` 每行就是这个 |
| loss | 模型输出与标准答案的差距（训练要最小化的数） | answer-only loss = 只对 assistant 部分计算 |
| epoch | 整个训练集过一遍叫 1 epoch | 太多 epoch → 背题（过拟合） |
| 过拟合 | 训练集分数高、新数据分数差 = 背题了 | 看 dev loss 是否回升 |
| train/dev/test | 课本 / 平时测验 / 期末考，三者绝不混用 | 实习生 4136/432/432 切分 |
| 数据泄漏 | 考题（或其变体）混进了课本 | 他的教训：消息级不重叠但答案哈希交集 196 |
| LoRA | 只训练插入的小矩阵而非全部权重，省显存省时间 | 3B 全量训练要多卡；LoRA 单卡就行 |
| QLoRA | 把基座压成 4bit 再挂 LoRA，更省显存 | 实习生用的就是 QLoRA(r=16) |
| 量化 | 权重从 16bit 压到 4bit 等，换取端侧可跑 | GGUF Q4_K_M 进 Ollama；量化会掉些分 |
| P / R / F1 | 精确率(说的里面多少对) / 召回率(该说的说了多少) / 两者调和平均 | 语素键选择的主指标 |
| 幻觉 | 模型编造输入/注册表里不存在的东西 | 他的数据：无操作样本上 32.9% 凭空加按钮 |

## 三、如何看数据：拿实习生的真实文件练手

### 练习 1：读一条种子样本

打开 `实习生数据整理/02-种子与扩展数据/01-V4种子144/seeds-144.jsonl` 任意一行
（每行一个 JSON，可以粘到任何 JSON 格式化工具里看）。抓四个字段就够：

- `user_prompt` —— 用户说的话（模型输入的一部分）；
- `runtime_context` —— 他喂给模型的"可信工具结果"（**注意：我们的架构没有
  这个**，这是两条路线的最大差异，见练习 4）；
- `target_frame` —— 标准答案；
- `provenance` / `contract_version` —— 数据从哪来、对应哪个版本的提示词契约。

**看数据的第一习惯：任何一条训练样本都要能回答"输入是什么、标准答案是什么、
答案里每个字段的依据在输入的哪里"。** 依据不存在 = 教模型幻觉。

### 练习 2：读一条 SFT 样本

`02-V4扩展5000/sft-train-4136.jsonl` 每行是 `{"messages":[system, user, assistant]}`：
system 是 5903 字符的固定规则书（他做了 SHA256 版本化，我们的
`evals/prompt-manifest.json` 学的就是这个）；user 是本条输入；assistant 是
标准答案——**训练时只有 assistant 部分计损失**（answer-only loss），也就是
"只考答题，不考抄题干"。

再打开同目录 `manifest-audit-5000.jsonl` 对照看：每行记录该样本的来源种子、
风格轴、split 归属。**审计信息单独存放、绝不混进模型输入**——这是他做得
非常对的地方，我们的 `tools/gen_training_data.py` 照搬了。

### 练习 3：读一份评测报告

打开 `02-V4扩展5000/finetune-evaluation-report-288.md`，按这个顺序看：

1. **先看实验设置**：训练 288 条×3 epoch、测试 288 条、temperature=0。
   分数没有设置就没有意义——别人问你"84% 是在什么条件下测的"你必须答得上。
2. **再看指标从上往下的"漏斗"**：JSON 合法率 100% → 模板命中 96.9% →
   可渲染 84.4% → 完整一致 38.5%。每往下一层要求更严。**增益在哪层、
   损失在哪层，决定下一步改什么**：他的 JSON 合法率训前就是 100%（约束
   解码的功劳），所以微调收益全部来自路由和字段，而不是"学会写 JSON"。
3. **然后看唯一变差的指标**：Profile 命中率 51%→47.6%。展开看诊断表才发现
   真相：该用的时候用对了（43%→90%），**不该用的时候不省略了**（52%→40%）。
   一个总分掩盖两个反向变化——**永远把"正例做对"和"负例不做"分开统计**。
4. **最后看逐条错误文件** `finetune-errors-288.jsonl`：抽 10 条自己读，
   给错误归类（他的高频错：把模板 ID 填进 profileKey、多写没依据的字段）。
   错误分类表 > 总分，因为它直接告诉你补什么数据。

### 练习 4：理解全篇最重要的一组对比数字

同一个模型：结构化输入离线评测**可渲染率 84.4%** → 纯自然语言真实页面
**严格通过 2/20**。为什么差这么远？他的离线输入里带 `runtime_context`
（答案素材都在输入里，模型只要"搬运"），页面实测是光秃秃一句人话。

**教训：你在什么输入分布上评测，分数就只对什么分布有效。** 我们的冻结
测试集因此规定只收纯自然语言（`evals/frozen/README.md` 第 2 条规矩）。

### 练习 5：看穿"记忆水分"

他的 one-shot 评测里 195/288 条测试题的标准答案与提示词里的示例**完全相同**。
按"答案相同/不同"分组重算：不同组的 Profile 准确率掉约 20 个百分点。
这就是记忆而非泛化。我们的 harness（`evals/run_frozen_eval.py --train-file`）
内置了同样的切片，训后评测必开。

## 四、模型训练十条军规（每条都有他的实例作证）

1. **评测先于训练。** 没有冻结集就开训 = 无法证明训练有效，也无法发现训坏。
2. **考题绝不进课本。** 文本级、近重复、事实级三层检查（`tools/check_leakage.py`）。
   他的 196 条答案哈希交集就是只查了第一层的后果。
3. **温度 0 + 固定随机种子 + 版本化提示词**，否则两次分数不可比。
   任何评测报告都要能回答"用的哪版 prompt"（我们绑定 `prompt-manifest.json`）。
4. **分数要分层看**（合法率→命中率→可渲染→完全一致），增益/退化定位到层。
5. **正例负例分开统计。** 微调容易教会"做什么"，很难教会"不做什么"——
   他的 Profile 边界实验是铁证。负例要靠成对边界样本 + 偏好优化（DPO）。
6. **训练样本必须复刻生产提示词。** 训练时 user 消息怎么拼（含候选键注入），
   生产就怎么拼；不一致 = 训了个别的任务。`gen_training_data.py` 已内置。
7. **小模型天然爱多做**：多加按钮、多填字段（他的幻觉率 32.9% vs 遗漏 0.2%）。
   评测里要有专门抓"多做"的指标（我们的 action_hallucination_rate）。
8. **先跑最小实验再放大。** 他用 288 条×3 epoch 就把模板命中拉了 24 个点——
   数据不是越多越好，是"分布对不对"的问题。先小跑、看错误分类、定向补数据。
9. **量化后要复测。** 端侧跑的是 Q4 量化版，分数以量化版为准（预期回退 ≤3 点）。
10. **诚实记录。** 他把 592/1 失败、34 条 TS 诊断、来源不明的文件变更全写在
    交接里且不回滚不掩饰——这不是道德要求，是工程要求：被掩盖的失败会在
    最贵的时刻爆炸。汇报时先说没做什么、什么没过。

## 五、本项目的训练工具箱（本次新增）

| 工具 | 干什么 | 什么时候跑 |
|---|---|---|
| `tools/make_prompt_manifest.py` | 冻结/校验提示词契约（SHA256） | 改动 prompt 前后；每次评测/造数据前 `--check` |
| `evals/frozen/` + `evals/run_frozen_eval.py` | 冻结集格式与评测 harness（含记忆切片、动作幻觉对、拒绝类假绑统计） | 基线、训后、量化后各跑一次 |
| `tools/check_leakage.py` | 训练集×冻结集三层泄漏检查 | 每次组装训练集后 |
| `tools/gen_training_data.py` | 注册表反向数据工厂（枚举骨架→云端反写 query→风格扩增+审计清单） | 阶段 2 |

各工具的具体命令与顺序见 [训练准备执行计划.md](训练准备执行计划.md)。

## 六、关于盘古 3B 与 CANN（未来迁移展望）

你未来要换到华为盘古 3B、在昇腾（Ascend）硬件上训练/推理。先建立对照概念：

| 你现在用的 | 华为侧对应物 | 说明 |
|---|---|---|
| NVIDIA GPU + CUDA | 昇腾 NPU + **CANN** | CANN 是昇腾的算力栈（驱动+算子库+编译器），角色类比 CUDA；应用层一般不直接写 CANN |
| PyTorch | MindSpore，或 **torch_npu**（昇腾版 PyTorch 插件） | 训练脚本要换后端；torch_npu 路线改动最小 |
| HuggingFace + PEFT (LoRA) | MindFormers / openMind 等套件（同样支持 LoRA） | LoRA/QLoRA 的思想完全一致，参数含义不变 |
| Ollama + GGUF 量化 | 昇腾端侧推理走 MindSpore Lite / OM 模型等 | 量化同样存在，量化后复测的军规不变 |

**关键结论：换模型换硬件,方法论一件不换。** 冻结测试集、评测 harness、数据
工厂、泄漏检查、提示词契约——全部与模型无关，现在在 qwen 上建好，将来直接
对着盘古复用。真正要换的只有三处：

1. **对话模板（chat template）**：每个模型家族的 system/user/assistant 拼接
   格式不同，SFT 数据要按盘古的模板重新包一层（内容不变，包装变）；
2. **tokenizer**：同一句话 token 数不同，重新核一遍长度上限与延迟账；
3. **训练/推理脚本的后端**：按当时的盘古官方文档选 MindFormers 或 torch_npu。

所以现在用 qwen 把整套流程跑通、把数据和评测资产沉淀好，就是为盘古做的
最好准备。到迁移时具体工具链请以华为当时的官方文档为准（这块迭代很快，
本文写作时的细节可能过时）。
